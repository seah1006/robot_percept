## 1. Root causes and evidence

### SAM2 low IoU: not demonstrated to be a SAM bug or current metric bug
- `web/app.py:178-204`: click calls `fresh_frame()` before segmentation. `Runtime.fresh_frame` sends refresh; `web/sim_worker.py` finishes commands with `publish(True)`, which forces RGB, depth AND segmentation render. `Runtime.frame()` copies all three under the same lock. `select_at` compares SAM mask to the SAME LOCAL `seg` captured before register, not a later live segment buffer. The IoU expression is ordinary boolean intersection/union. Current stale-seg allegation is therefore unsupported.
- RGB is MuJoCo `r.render()` RGB, handed unchanged to `predictor.set_image`. RGB->BGR conversion is confined to display/PNG writing. Installed `sam2.1/sam2/sam2_image_predictor.py:86-130` explicitly expects RGB.
- `predict(...point_coords=[[x,y]], point_labels=[1], multimask_output=True)` is correct. JS maps displayed coordinates to `naturalWidth/Height`; backend bounds-checks. Predictor normalizes pixel XY itself and returns masks at ORIGINAL H,W (`:237-303`, `:431`), not low-resolution logits. No resolution/XY/RGB bug found.
- `web/perception_stub.py` selects `argmax(scores)` across three masks and discards alternatives. A score ranks predicted mask quality, not necessarily whole-object extent. A click on cap/part can legitimately choose a partial object. FP can still register accurately from that partial depth support. Concrete saved evidence: `web/test_results_fp.json` run 2 has mustard IoU .1525 at pixel [353,192], pose error 1.482 mm / .804 degrees. The draft's exact 11% instance was not independently replayed.
- Conclusion: real low whole-object-mask quality exists in saved evidence, but exact cause remains undetermined. Single-point part/whole ambiguity is the leading testable hypothesis, NOT a confirmed model defect. First save RGB/depth/GT seg, exact click, all three masks/scores/areas/IoUs and chosen index. Freeze each failing frame for replay. Check whole-object target identity separately: current `name=argmax GT overlap` is an oracle association valid for simulation evaluation only, not deployable recognition.
- Residual engineering issues: RGB/depth/seg copy and status metadata are not one atomic frame packet; moving object/camera can misalign pose GT and frame metadata. User clicks an older MJPEG frame but inference deliberately takes a fresh one. Carry frame_id/capture timestamp/camera transforms with a packet; distinguish this from the unsupported current static stale-mask claim. SAM overlay remains registration-time mask during tracking, so label or clear stale overlays.

### Grasp p95 tail: concrete nested IK search
- `sim/grasp.py:113-160`: tall mustard bypasses the short-object fast path. For each candidate it searches seed groups (2 then 9 seeds), solves pregrasp/grasp, and continues across all candidates to minimize cost instead of accepting the first feasible one. `sim/ik.py:79` executes `max_iters * 10`: default 160 means up to 1600 iterations plus internal random restarts, nested inside external seeds. Even fast max_iters=16 can mean 160 iterations.
- CPU-only quick sample with `OPENBLAS_NUM_THREADS=1`, one object, no rendering, seed 0..4: mustard choose_grasp seconds [.536, 5.136, .064, .204, .172]. Seed 1: 12 IK calls, 8 failed, longest single IK .665 s. Seed 7 profile: mustard 6 candidates, .241 s and 428 mj_forward calls; box 4 candidates, .0166 s and 14 mj_forward calls. Small diagnostic sample, NOT a new p95 claim. Confirms failed IK search tail rather than GPU/SAM cost.
- Design: expose explicit iteration/restart/total-call budgets without silently redefining existing max_iters semantics; instrument candidate/mode/seed/iterations/failures. Add short warm-start pass to tall objects, rank candidates cheaply, stop at feasible solution under an agreed quality threshold, then retain bounded fallback. Cache model indices and reusable scratch data where profiler warrants it. Preserve endpoint collision checks and existing tolerances; do not claim path collision safety from endpoint checks.

### Tracking margin and metric
- `notes/fps_changes.md`: independently recorded 8.89-11.72 FPS under varying GPU load; explicitly sampled reciprocal inference durations, NOT actual update throughput. `Runtime.track_loop` sets tracking_fps=1/call duration; it excludes pacing/gaps and does not count committed distinct updates. Existing offline ~14 FPS is GT-seeded static isolation, not general moving-scene E2E performance.
- Add update_count, consumed frame_id, capture/finish timestamps, source-frame age, successful_updates/elapsed, latency p50/p95, failure count and busy/paused duration. Time CUDA with synchronization only at benchmark boundaries. Report dedicated GPU and contended runs separately, warm-up separately. Do not promise >=10 under arbitrary shared contention.

### Evaluation validity caveats
- `sim/export_fp.py:147` rejects non-mustard; `_create_env:85` forces reset(randomize=False). Its existing CLI cannot provide the proposed 3-object random suite unchanged. `_apply_motion` also hardcodes default mustard body; parameterize target name.
- `eval/pose_metrics.py:51` computes intersection of predicted and GT filenames. Missing frames are listed but excluded from accuracy averages/AUC. A new harness must count missing predictions as failures, not reward dropped hard frames.
- `sim/control.py:266-313` place uses actual object_pose_fn to infer held relative transform, correct XY error twice and check release height; pick reads true z0; attach uses exact sim poses. Therefore current FP pick/place is GT-assisted simulation, not a wholly perception-only control evaluation. Explicitly label oracle feedback and weld; ideally separate GT evaluator callbacks from estimated control callbacks and provide assist/oracle flags. Turning weld off requires a real switch (currently unconditional after bilateral contact), not just a report label.

### 3. Depth/appearance robustness [M-L, follows fixed harness]
