## 1. 기술 실현성: 치수 해석

### 1.1 YMX(산업용, 구형 손목): 해석 지지됨, 기준점은 명시 필요
치수표에서 다음 항등식이 **정확히** 성립함(1210/2510/14200/9200/9200L 5개 모델, 단위 mm).

| 항등식 | 1210 | 2510 | 의미 |
|-|-|-|-|
| H = A + C + √(D²+E²) | 1420.6 vs 1420 | 1761.1 vs 1761 | 최대 반경 = **손목중심(P-point)** 기준 |
| G = C + √(D²+E²) | 1260.6 vs 1260 | 1601.1 vs 1601 | J2→손목중심 |
| I = G − A | 1100 = 1100 | 1441 = 1441 | 후방 도달거리(J1축 뒤) |
| J = B + C + D | 1132.6 = 1132.6 | 1430 = 1430 | 영점 자세(상완 수직·전완 수평)의 전완선 높이 → **B=설치면→J2 높이, D=J3 위쪽 오프셋 확정** |
| L = J + K | 1949.6 = 1949.6 | 2490 = 2490 | K = 전완선 위로 올라가는 높이 |
| M − (H+I) | −55 | −71 | M은 J2 후방 한계로 잘린 폭으로 추정 |

- YMX-5200 행은 I=1596(G−A=1608), L=2489(J+K=2991)로 맞지 않음. 9200 행과 비교하면 카탈로그 오타로 보임. 문서에 각주로 남길 것.
- **지적 1 (중요)**: 최대 반경 1420은 손목중심 기준임. 플랜지 기준으로 재면 A+C+√(D²+(E+F)²) = 1533.1로 +8%가 됨. 합격 기준과 화면에 기준점(손목중심 = J4·J5·J6 축 교점)을 명시해야 함. F(115)는 손목중심→플랜지(d6)로 보는 게 맞음. "P-point"는 일본·한국 카탈로그에서 보통 손목중심을 뜻하니, yuil_specs.md의 "F=J5→플랜지(P-point)" 표기는 "F = P-point(손목중심)→플랜지"로 고쳐야 함.
- **지적 2**: 같은 치수로 만든 모델의 반경을 ±0.5%로 검사하는 건 동어반복임(항상 0.04%가 나옴). 대신 **관절 한계를 넣은 MJCF에서 FK 몬테카를로로 작업영역을 샘플링**해서 I(후방 도달)·J·L(최고점)·M을 재현하는지 보고, 이 값들로 J2·J3 한계를 역추정하자(K·M이 한계 의존 값).
- DH(표준 DH, base = 설치면): d1=387.6, a1=160, α1=−90°; a2=595; a3=150, α3=−90°; d4=648.5, α4=+90°; α5=−90°; d6=115. 계획서 값과 일치함. 빠진 것은 **θ 오프셋**(카탈로그 영점은 상완 수직이라 θ2에 −90° 오프셋이 필요)과 각 관절 회전 방향 부호. 이 둘을 표로 고정할 것.
- 구형 손목(a4=a5=d5=0)이라 해석해 8개(어깨 2 × 팔꿈치 2 × 손목 2)를 쓸 수 있음.

### 1.2 YBL(협동, UR형): D는 확정, E·F 배정은 미확정
| 항등식 | A603 | A606 | A612 | A620 |
|-|-|-|-|-|
| G = B + C + D | 624 = 624 | 922.5 = 922.5 | 1324 = 1324 | 1496.7 = 1496.7 |
| H = C + D | 346.2 vs 346 | 501.15 vs 501.1 | 698 = 698 | 785 = 785 |
| K = B + C | 538 = 538 | 824.5 vs **829** | 1226 = 1226 | 1386.7 vs 1387 |
| √(L²−G²) | 86.7 | 132.7 | 103.0 | 113.5 |

- D는 펴진 팔 방향으로 일직선 더해지는 오프셋이라 **D = d5**(UR DH의 J4→J5)로 확정. UR10e도 a2+a3+d5 = 1301.7 ≈ 공식 도달거리 1300으로 같은 정의를 씀(반면 UR5e는 916.9 vs 850으로 정의가 다름).
- A = d1(설치면→J2), B = a2, C = a3. 계획서와 같음.
- **지적 3 (중요)**: 계획서에는 "손목 오프셋 98·82·128"만 있고 **E·F 중 어느 쪽이 d4(측면 오프셋 합, 측면도에는 안 보이는 깊이 방향)이고 어느 쪽이 d6(J5→플랜지)인지 배정이 없음**. 치수표만으로는 결정할 수 없음.
  - 대안 O-1: d4=F(128), d6=E(82). UR5e(d4 133 > d6 99.6)처럼 d4가 더 큰 경우와 비슷함.
  - 대안 O-2: d4=E(82), d6=F(128). F가 모델별로 많이 달라짐(86.5→163)을 툴플랜지 돌출로 보는 해석.
  - L을 √(G²+x²)로 풀면 A612에서 x는 96~109mm(L 반올림 범위)로 나와서 E·F 둘 다 맞지 않음. A606 132.7, A603 86.7로 모델마다 일관성도 없어서 L은 근거로 쓰지 않음.
  - UR의 J2–J3 측면 오프셋(어깨 138·팔꿈치 −131)에 해당하는 값은 카탈로그에 없음. 모델에서는 그 순합을 d4 하나로 둔다고 명시할 것.
  - 결정: 단계 A에서 카탈로그 정면도·사진으로 판별하고, 안 되면 O-1을 기본으로 하되 "추정" 표기와 대안을 문서에 남김. d4가 내부 특이 원기둥 반경(어깨 특이점)을 정하므로 시연 문구에도 영향이 있음.
- I(848.8 등)·J(242 등)는 단순 조합으로는 설명되지 않음 → 합격 기준에 쓰지 않음.
- UR형이라 d4≠0이어도 해석해 8개(Hawkins 방식)를 그대로 쓸 수 있음.

### 1.3 UR5e 기준 로봇: 그대로면 합격 기준이 FAIL
- Menagerie ur5e.xml의 링크 값과 UR 공개 DH 차이: d1 +0.5mm(0.163 vs 0.1625), a3 −0.2(0.392 vs 0.3922), d4 +0.7(0.138−0.131+0.127=0.134 vs 0.1333), d5 +0.3, d6 +0.4mm. 베이스에도 quat 0 0 0 −1(z축 180° 회전)이 있음.
- **지적 4 (중요)**: "공개 DH FK vs MuJoCo ≤1µm"는 성립하지 않음. 수정안: ① MJCF에서 추출한 DH + 베이스 변환으로 ≤1µm·≤1e-6rad를 확인(float64 FK면 1e-12 m 수준이라 충분히 가능), ② 공개 DH와 Menagerie의 차이는 별도로 ≤1mm로 보고. 1µm 검사 중 **UR5e만이 독립 모델과 비교하는 의미 있는 검사**이고, YMX/YBL은 생성기 회귀 검사라는 점을 문서에 명시.

## 2. 구조

- **지적 5**: 새 `web/arm_worker.py`(MuJoCo 오프스크린 렌더 + JPEG 30fps, 별도 프로세스)는 과함. humanoid_worker는 220줄이고 수명주기·고아 프로세스 방지·종료 테스트(test_shutdown, process_lifecycle)까지 따라와야 함. 그런데 계획서의 3D 요구(관절 좌표축·이름·강조·점구름)는 three.js가 훨씬 쉬움. 기구학은 운동학만 다루므로 동역학 시뮬도 필요 없음.
  - 수정안(권장): **브라우저 three.js 렌더 + Flask 프로세스 안의 경량 `ArmRuntime`**(numpy DH 계산, 6R FK+J는 수십 µs, MuJoCo 모델은 mj_kinematics 비교용으로만 로드하고 렌더러는 없음).
  - FK/IK는 `POST /arm/joints`·`/arm/target`의 응답으로 바로 결과를 돌려줌. 왕복 지연이 가장 짧음.
  - 푸시는 기존 `/status/ws` 스케줄러에 'arm' 빌더를 추가해 활성 시 10Hz로 보냄. status-stream.js는 이미 `type+'-push'` 이벤트를 범용으로 쏘므로 수정이 필요 없음.
  - 30fps 기준은 브라우저 requestAnimationFrame 30초 창으로 측정. 서버에 GL 의존이 없어서 집 AMD PC에서도 동작함.
  - MuJoCo 렌더 영상이 꼭 필요할 때만(v2) humanoid_worker를 복제한 arm_worker를 만듦.
- 페이로드 실측(python): A·T 각각 3×4×6, J 36, q·qd, 자세 등 약 230개 수. 유효숫자 6자리면 2.1KB, `json.dumps` 0.25ms + 반올림 0.36ms. 17자리면 4.2KB에 0.41ms. 15Hz면 CPU 1% 미만, 31KB/s라 부담 없음. A_i는 DH표+θ로 JS에서 다시 계산할 수 있지만, 정답 소스를 하나로 두기 위해 서버 값을 보내는 쪽을 권장함.
- 모드 배타: arm 모드에 들어가면 G1 worker를 정지하고 teleop을 끄고 Panda 영상 src를 제거해야 함(humanoid.js가 G1 전환 때 하는 것과 같음). 문서에 명시.
- **지적 6**: `sim/humanoid_ik.py`의 ArmIK는 G1의 site·팔꿈치 목표·MuJoCo 모델에 묶여 있어서 "재사용"이 안 됨. 가중 DLS + 조작성 감쇠 공식만 가져와 `arm_kinematics`에 DH 기반 numpy로 새로 작성해야 함.

## 3. 합격 기준

| 계획서 기준 | 문제 | 수정안 |
|-|-|-|
| 최대 반경 ±0.5% | 동어반복, 기준점 미명시 | 손목중심 기준 명시 + 관절 한계를 넣은 FK 몬테카를로(1e5 샘플)로 YMX I·J·L, YBL H·K 재현 ±2% |
| FK vs MuJoCo ≤1µm·1e-6rad | UR5e 공개 DH로는 FAIL | MJCF 추출 DH로 ≤1µm. 공개 DH 차이는 ≤1mm 보고. 시드 고정, 관절 한계 내 균일 샘플 |
| 자코비안 상대오차 ≤1e-6 | 정의 모호 | ‖J−Jn‖_F/‖Jn‖_F, 중앙차분 h=1e-6. 추가로 mj_jacSite와도 비교 |
| IK 98%·p95 33ms | 느슨함, 목표·성공 정의 없음 | 목표 = 무작위 q의 FK(위치+자세). 성공 = 위치 ≤0.1mm·자세 ≤1e-3rad. 해석해 100%·p95 ≤1ms, 수치 DLS ≥98%·p95 ≤10ms(함수 호출 기준). HTTP 왕복 p95는 별도(≤100ms, R4-C 안) |
| 특이점 100%/오경고 ≤1% | '정답'과 '일반 자세'가 정의되지 않음 | 정답 = 해석적 det 인수(UR: s3, s5, a2c2+a3c23+d5s234 / 구형손목: s5, 어깨 = 손목중심의 J1축 거리, 팔꿈치 = s3 계열) 또는 정규화 J의 σmin. 경고 임계 ε1, 일반 자세 = 인수 > ε2(=2ε1)로 히스테리시스 밴드 제외. 해석 det vs 수치 det 일치도 테스트 |
| 렌더 ≥29.7fps | 측정 주체 불명 | 브라우저 rAF 30초 창(three.js 안). 서버 쪽은 Panda·G1 fps 회귀만 |

빠진 테스트:
- 해석해 8개 전부를 FK로 역검증(≤1e-9 m).
- 해 선택: 관절 한계 안 + 현재 q 최근접(가중), 같은 입력이면 같은 결과(결정론).
- 연속성: 직선 경로 100스텝에서 분기 점프 없음(스텝당 |Δq| ≤5°, 특이 밴드 구간 제외).
- 해석 vs 수치: 수치해 결과가 해석해 집합 중 하나와 ≤1e-6 rad로 일치.
- 관절 한계: IK 결과·슬라이더·API 입력에서 위반 0, 범위 밖이면 400.
- 자기충돌·바닥: 단순 형상 MuJoCo 접촉(인접 링크 제외)으로 **경고만**(회피는 범위 밖). 알려진 충돌 자세 1개 이상, 일반 자세 오경고 측정.
- 입력 검증: NaN·inf·길이·크기 제한, origin 검사(기존 realtime의 origin_allowed 재사용).

## 4. 단계·병렬화·소유 파일

- **지적 7 (중요)**: 로봇 선택 `<select id="h-mode">`는 index.html이 아니라 **web/static/humanoid.js가 동적으로 만듦**. onchange도 `g1`이 아니면 전부 Panda로 처리해서, arm 옵션을 넣으려면 humanoid.js 수정이 필수임(P1c S 페어가 최근 수정한 파일). `/status/ws`에 빌더를 넣으려면 web/realtime.py의 `register_realtime(app, robot_status, teleop, humanoid)` 시그니처도 바꿔야 함.
  - 공유 파일 = web/app.py, web/templates/index.html(arm.js 스크립트 1줄), **web/static/humanoid.js, web/realtime.py**.
  - humanoid.js 수정 최소안: `h-mode`에서 panda/g1 외의 값은 무시하고 `robot-mode` CustomEvent만 보내게 바꿈(5~10줄). 나머지는 arm.js가 처리. S 구현자와 순서를 합의하고 한 번에 반영.
- 순서 수정안:
  - B0(범용 DH·FK·J·해석 IK + UR5e 검증)은 YUIL 해석과 무관하니 A와 병행.
  - B 시작 때 **payload 계약(JSON 스키마)**을 먼저 고정하면 D를 목업 데이터로 동시에 시작할 수 있음.
  - V-A는 B와 동시에 독립 구현(PoE 방식 등)으로 검증 하네스를 작성.
- 예상 소요(에이전트 작업 기준): A 0.5일, B 1~1.5일, C 0.5일(in-process라 축소), D 1.5~2일, E 1일 → 약 5일. Codex 한도 때문에 단일 구현자 직렬이면 더 늘어날 수 있음.

## 5. 빠진 것·과한 것

빠진 것:
- DH 규약(표준 vs Craig 수정 DH), 단위(화면 mm, MuJoCo m), θ 오프셋·회전 부호, 베이스·TCP 정의(툴 오프셋 파라미터).
- 관절 한계·속도 추정 근거(같은 반경 클래스의 공개 사양을 참고했다고 출처 명시).
- 프리셋 JSON(R4-C 안)을 pytest 수치 회귀로 고정.
- 모드 배타, 홈 PC(GPU 없음) 동작 조건.

과한 것(v2로 미룰 것): 서버 MuJoCo 렌더, 3D 목표 드래그 기즈모, CSV 내보내기, 실시간 점구름(정적 사전계산 JSON으로 대체), 같은 경로 소요시간(J1~J5 속도가 추정값이라 숫자 신뢰도가 낮음).

## 6. R4-C와 합의/이견
왕복 1회로 합의 완료. R4-C 측 기록은 notes/plan_r4_review_c.md.

- 합의(R4-C가 K1~K7 전부 수용):
  - 치수 해석과 기준점 명시(손목중심), YBL E·F 대안 O-1/O-2를 문서화하고 '추정' 표기.
  - UR5e는 MJCF 추출 DH로 ≤1µm, 공개 DH 차이는 별도 보고.
  - three.js 렌더 + in-process ArmRuntime + POST 응답·/status/ws 'arm' 빌더. arm_worker는 v2.
  - 공유 파일에 humanoid.js·realtime.py 추가, S 페어와 순서 합의.
  - IK·특이점 기준을 위 표대로 정의하고, 빠진 테스트 추가.
  - B0와 A를 병행, payload 계약을 먼저 고정.
- R4-O가 R4-C 안을 수용한 것:
  - MVP 순서: 모델 + FK/DH/행렬 → A_i 누적 스텝퍼(클라이언트 계산) → **특이점 경고**(비교보다 앞) → IK → 두 로봇 비교 → 자코비안 히트맵.
  - 3분 시연 프리셋 4개를 JSON으로 고정하고 pytest로 회귀 검사.
