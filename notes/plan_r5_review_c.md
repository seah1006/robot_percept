# r5 계획서 검토 R5-C (사용자·실용·검증 관점) - 초안 제안 (R5-O 회신 전)

검토 대상: notes/plan_r5_grounded_picking_cell.md v1. 읽기 전용 검토.

## 0. 총평
방향(말로 지시 -> 인식 -> 실행 -> 이력)은 설득력 있고 백엔드 강점과 맞다. 문제는 (a) 범위가 5단계로 넓고 (b) "실용성" 문구가 시뮬 데모 수준을 넘어 보일 위험 (c) 합격기준에 사용자 체감 지표가 없다는 점.

## 1. 실용성 스토리 (P0 문구 수정)
- 연결 가능한 실제 사례: 소량 다품종 분류/피킹(물류 오더 피킹, 반품 분류), 작업자가 품목명을 말로 지시하는 간이 셀. 근거: 개방형 어휘 검출은 새 품목 재학습 부담을 줄이는 방향이 실제 연구/제품 흐름.
- 과장 금지: "공장 투입 가능", "MES/SCADA 연동" -> "MES 흉내 지표(사이클 타임, 성공률)". 유일로보틱스 "결이 같다"는 취업 맥락 외 공개 문구에선 비제휴 표기 유지.
- 정직한 한계를 스토리에 포함: 산업 현장은 조명·반사·겹침·안전인증(ISO 10218/TS 15066)이 지배적이고, 이 프로젝트는 책상 평면 가정 + 시뮬 실행. 웹캠 부분은 "인식+위치 추정까지 실물, 집기는 시뮬"이라고 못박기.
- 3분 시연 흐름: (0:00) 실제 책상 웹캠 + 컵/상자 -> (0:30) 한국어로 "컵은 왼쪽 상자" 입력, 검출 박스 오버레이 -> (1:00) 시뮬 트윈에 같은 배치 생성, 위치 오차 mm 표시 -> (1:30) 로봇이 집어 적재, 상태 머신 단계 표시 -> (2:15) 일부러 애매한 지시 -> needs_help 후보 확인 UI -> (2:45) 이력/사이클 타임 표 1화면.
- 면접 핵심 질문(답 준비): 1) 왜 Grounding DINO이고 대안/라이선스는? 2) 웹캠 한 장에서 3D 위치는 어떻게(평면 투영, 보정, 오차)? 3) 오인식 시 어떻게 안전하게 처리(임계값, needs_help)? 4) 작업 큐/상태 머신을 왜 그렇게 설계(멱등성, 실패 재개, 동시 요청)? 5) 시뮬 성능과 실물 성능의 차이를 어떻게 분리 보고? 6) GPU 직렬화/지연 설계.

## 2. 범위: MVP 컷 (P0)
- MVP = 1단계 + 2단계 축소(보정 + 실시간 오버레이 + 평면 좌표, 트윈 동기화는 "스냅샷 1회 생성"로 시작) + 3단계 + 최소 대시보드(성공률/사이클 타임/최근 작업 1화면, 4단계의 일부).
- v2로: 손가락 지시, 원격 조종 연결, 저주파 연속 트윈 갱신, Wilson CI 외 상세 분석, FoundationPose/RealSense 경로, 5단계 r4 티칭 탭(전체), 유일 협동로봇 교체, LLM 한국어 해석, Docker.
- Docker/영상/README 마감은 MVP에도 필요(포트폴리오): "5단계"에서 티칭 탭만 분리하고 배포·3분 영상은 MVP에 포함.
- 단계 병행 계획: 공유 파일 한 구현자 규칙상 K와 W2 병행은 병목 -> 순서 G -> W2(보정) -> K 권장.

## 3. 합격 기준 보강 (P0)
추가 항목:
- 사용자 체감: 지시 입력 -> 검출 오버레이 표시 p50/p95, 지시 -> 집기 시작, 지시 -> 완료 (각각 GPU/CPU 환경별 분리). 목표값은 1단계 측정 후 확정(임의 숫자 금지).
- 오인식 경험: 저신뢰/복수 후보일 때 사용자가 확인 화면까지 도달하는 시간, "확인 없이 잘못 집음" 비율을 시뮬/실물 분리 보고.
- 정직성 라벨: 모든 지표에 [시뮬 GT] [시뮬 인식] [실물 웹캠] 출처 배지, GT 보조 사용 시 UI에 상시 표시. 실물 표본이 작으면 N과 조건(조명, 물체 3종)을 명기하고 일반화 주장 금지.
- 시뮬 도메인 갭: Grounding 정확도를 시뮬 렌더와 실물 웹캠 양쪽에서 각각 측정, 시뮬 수치를 실물 성능처럼 인용 금지.
- 영상 품질 대신 "실패 케이스 갤러리"(오인식 사례 5개) 포함 - 정직성 가점.
- 비개발자 리허설: 사용자 본인이 3분 설명 가능한지(PASS 근거 아님).

## 4. 위험 (개인정보·라이선스·표기) (P0)
- Grounding DINO: 코드 Apache-2.0이나 가중치/HF 모델 카드 라이선스, 학습 데이터 출처를 모델 카드에서 직접 확인 후 표에 기재(계획서 "확인 필요" 상태 유지, 단정 금지). OWLv2/Florence-2도 같음. 상업 이용 계획 없으면 위험 낮지만 표기 필수.
- 웹캠: 방/얼굴/가족이 찍힐 수 있음 -> 'person' 제외는 검출 결과 필터일 뿐 프레임 자체는 서버로 전송됨. 프레임 저장 OFF, 로그에 이미지 미기록, 시연 영상/스크린샷 공개 전 배경 정리, 교수님 시연 시 촬영 범위 안내. 이력 DB에 이미지 대신 박스/점수만.
- 근사 모델 표기: 로봇 모델이 실제 제품이 아닌 Panda 또는 근사 모델이면 UI/README 상시 "근사 모델, 제조사 비제휴" 문구(r4 규칙 유지).
- 안전 표기: "충돌 검사·안전 감속"은 시뮬 기능이며 안전 인증 아님.
- 5080 서버 금지 규칙, 8GB GPU 공유 정책 유지.

## 5. 사용자 확인 질문 권장 답
1. 로봇: Panda로 시작. 이유: MVP 리스크 축소, 기존 sim/grasp 재사용, 유일 교체는 v2(근사 모델 정직성 부담).
2. 물체: 서로 다른 색/형태가 뚜렷한 3개(예: 머그컵, 작은 박스, 음료 캔/병) + 상자 2개. 투명/반사/아주 작은 물체 제외. 사전 사진으로 Grounding 점수 사전 확인 후 확정.
3. 깊이 카메라: 대여 가능해도 MVP에선 불필요, 평면 가정으로 진행하고 v2 확장으로 표기. 없어도 진행.
4. P1c 중단: 동의 권장. 포트폴리오 서사 집중, 기본 OFF 유지로 회귀 위험만 관리.

## 6. 남은 R5-O 확인 사항(회신 대기)
- Grounding DINO 구현 현실성(transformers 버전, 8GB VRAM, 지연), 상태 머신/큐 구현 비용, MVP 컷 동의 여부, 공유 파일 병목.

# 합의안 (R5-C + R5-O, 왕복 1회: C 제안 -> O 구현 지적 7건 -> C 전부 수용)

## A. 우선순위
P0 (구현 전 계획서 반영)
1. MVP 컷 확정: 1단계 + 2단계 축소 + 3단계 + 최소 대시보드 1화면 + README/3분 영상. v2: 손가락 지시, 원격조종, 연속 트윈/추적, 원본 still(1280), FP/RealSense, r4 티칭 탭, 유일 로봇 교체, LLM 한국어, FP 포함 Docker.
2. 순서 G -> W2(보정) -> K. 공유 파일 한 번에 한 구현자.
3. 1단계 0번 작업: env 복제본에서 transformers 버전 pin을 rp_constraints로 설치 시험(torch 2.14/numpy 2.5.3 끌어올림 방지), v5 API 인자명 차이 봉인.
4. GPU: 별도 CUDA 프로세스 금지. 기존 perception worker에 op 'ground'/'segment_box' 추가, 사용 후 CPU 오프로드, 직렬화·G1 defer 재사용, op별 lazy import(박스만/CPU 모드 지원).
5. 합격기준 보강: 체감 지연(지시->오버레이/집기 시작/완료 p50/p95, 목표는 1단계 측정 후 확정), 출처 배지 [시뮬GT][시뮬인식][실물웹캠][녹화영상], gt_assist OFF E2E 필수 보고, 실패 케이스 갤러리.
6. 표기/개인정보: DINO 가중치·모델카드 라이선스 직접 확인(단정 금지), 프레임 저장 OFF·DB엔 박스/점수만, 'person' 제외는 필터일 뿐 프레임은 서버로 감을 명시, 근사 모델·비제휴·"안전 감속은 시뮬 기능, 인증 아님".
7. 스토리 문구: "MES 연동"이 아니라 "MES 흉내 지표", 공장 투입 가능 주장 금지, "인식+위치 추정은 실물 웹캠, 집기는 시뮬".
P1
8. "실시간 오버레이"를 "요청 시 1회 + 재탐지 버튼"으로 정정(작업 시작 시 1회와 모순 해소).
9. 시뮬 평가 자산 확장(색 다른 primitive/YCB 일부, 라이선스 확인, bin 자산은 Panda 회귀·eval 시드 영향 점검). 통계: 기본 N>=100 점추정+Wilson CI 병기, "CI 하한 >=90%"를 원하면 N≈200(사용자 선택).
10. 평면 투영 높이 편향(60mm 컵 약 30mm): 물체 높이 사전값 보정 + UI 입력. 시뮬은 GT 기하로 평가, 실물은 인쇄 격자 기준점. 위치오차 목표는 보정 후 측정치로 확정.
11. 트래커: MVP는 기존 preview 프레임 사용, 원본 still 라우트는 v2(PASS 재검증 비용). 카메라 일정 의존이므로 2단계 완료 조건에 "녹화 mp4 + 시뮬" 대체 허용([녹화영상] 배지 분리).
12. /tasks 누락 보완: 로봇 소유권 락(수동 pick·teleop·G1 상호배제), 취소/비상정지, 상태별 타임아웃, 다물체 하위 step, 재시작 시 running->interrupted, needs_help 타임아웃, 목적지 존 정의, StatusSchedule에 'cell' 키 추가.
13. Docker는 "박스만+시뮬" 이미지로 한정.
P2: 대시보드 상세 분석, 손 지시.

## B. 3분 시연 흐름 / 면접 질문
초안 섹션 1 유지(웹캠 책상 -> 한국어 지시+박스 오버레이 -> 트윈 배치+오차 mm -> 집기·상태 머신 -> 애매한 지시 needs_help -> 이력/사이클 타임). 카메라 불가 시 녹화 mp4로 대체하고 화면에 배지 표시.
면접 질문 6개는 섹션 1 유지(모델 선택/라이선스, 평면 투영 오차, 오인식 안전 처리, 큐·상태머신 설계, 시뮬 vs 실물 분리, GPU 직렬화).

## C. 사용자 확인 질문 권장 답
1. Panda로 시작, 유일 로봇은 v2.
2. 색·형태 뚜렷한 3개(머그컵, 작은 박스, 캔/병) + 상자 2개. 투명·반사·작은 물체 제외. Grounding 점수 사전 사진 확인 후 확정.
3. 깊이 카메라는 MVP 불필요(v2). 없어도 진행.
4. P1c 중단 동의(기본 OFF 유지, 회귀만 관리).

## D. 남은 이견
- 없음 (N 기준만 사용자 선택 사항). 단 grounding-dino 지연·VRAM(추정 100~300ms, 1~2GB)은 측정 전 미확정.

## E. R5-O 단서 2건 (합의 반영, 최종)
- [녹화영상] 경로: 기존 회사 녹화 mp4는 체커보드/ArUco가 없어 보정 불가 -> grounding 선택·오버레이만 검증, 위치 오차는 "측정 불가"로 명시. 보정판과 함께 새로 녹화(얼굴 비포함 구도)하면 위치 오차도 측정 가능.
- 물체 높이 사전값: 1차는 vocab 설정 파일(물체명 -> 높이·footprint·대칭)에 두고, UI 입력은 미등록 물체용 보조 수단.
- 남은 이견: 없음.
